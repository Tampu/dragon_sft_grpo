# DRAGON: QA-conditioned visual grounding — generic SFT → GRPO → eval

A plug-and-play sibling to `dragon_sft_grpo` (which fine-tunes InternVL3-8B
specifically). This repo runs the same task -- SFT then GRPO then
per-domain test-split evaluation, on the same six diagram/chart/map QA
datasets -- against **any** Hugging Face vision-language model that
`transformers`' `AutoModelForImageTextToText` / `AutoProcessor` pair
supports, with the model itself selected by a small JSON config rather than
hard-coded into the scripts.

**The task.** Given an image + question + the correct answer, predict the
bounding box(es) that *justify* that answer. Pure grounding: the model is
never shown candidate regions to choose from, it must localize them itself.

> Read [`DATASET.md`](DATASET.md) for exactly what data each stage sees --
> this pipeline's filter/split policy is deliberately simpler than (and
> different from) `dragon_sft_grpo`'s, see that file for why.

**Coordinates**: integers in `[0, 1000]`, `xyxy`, normalized to image
width/height, as a plain JSON array -- e.g. `[[182, 5, 466, 288], [137,
212, 272, 288]]`. No special tokens, no per-model native syntax. See
`scripts/grounding_prompts.py`'s docstring for why a shared, model-agnostic
convention was chosen over trying to match each candidate model's own
native grounding format.

## 0. Layout

```
dragon_vlm_sft_grpo/
  configs/models/<name>.json   one file per pluggable model -- see §1
  scripts/          shared, model-agnostic core: data building, prompts,
                     box geometry, LoRA/checkpoint I/O, the SFT trainer
  dragon_grpo/       GRPO training + evaluation
  <symlinks>         split_reviewed-2, Diagram_Attribution_Dataset,
                      hf_home, outputs (recreate after cloning, see below)
```

Every script resolves data as `Path(__file__).resolve().parents[1] /
<name>`, so this directory structure is load-bearing.

### Setup after cloning

This repo contains **code only**. Recreate these links at the repo root:

```bash
cd dragon_vlm_sft_grpo
for d in Diagram_Attribution_Dataset split_reviewed-2 hf_home outputs; do
  ln -s /path/to/your/$d $d
done
```

| link | what it must point at |
|---|---|
| `Diagram_Attribution_Dataset` | source images for all six domains |
| `split_reviewed-2` | raw per-question JSON (`Train/`, `Val/`, `Test/` per domain) |
| `hf_home` | HF cache -- set `HF_HOME` to this before running anything, or `from_pretrained` fills your home-directory cache instead |
| `outputs` | where LoRA checkpoints are written |

`dragon_datasets/` (built pools, converted JSONL) is generated by the data
pipeline below, not something you need to provide.

```bash
pip install -r requirements.txt
```

Unlike `dragon_sft_grpo`, there is no hand-pinned CUDA/flash-attn/
transformers-version combination baked in here -- see `requirements.txt`'s
header for why, and check your chosen model's own HF page for its minimum
`transformers` version before installing.

## 1. Plugging in a model

Everything model-specific lives in one JSON file under `configs/models/`.
`configs/models/qwen3vl_8b_thinking.json` is the one shipped here. To add a
different model, copy it and change the fields that actually differ:

```json
{
  "name": "my_model",
  "model_id": "org/repo-name",
  "model_class": "AutoModelForImageTextToText",
  "processor_class": "AutoProcessor",
  "trust_remote_code": false,
  "torch_dtype": "bfloat16",
  "attn_implementation": "flash_attention_2",
  "enable_thinking": false,
  "lora": {"r": 16, "alpha": 32, "dropout": 0.05, "target_modules": "all-linear"},
  "generation_defaults": {"max_new_tokens": 512, "do_sample": false, "num_beams": 1,
                          "repetition_penalty": 1.0, "no_repeat_ngram_size": 6},
  "grpo_generation": {"max_new_tokens": 512, "temperature": 1.0, "top_p": 1.0,
                      "no_repeat_ngram_size": 6}
}
```

Every script in `scripts/` and `dragon_grpo/` takes `--model-config
configs/models/<name>.json` and is otherwise identical code -- see
`scripts/model_config.py` for exactly what each field controls and why
`target_modules: "all-linear"` (peft's built-in auto-discovery of every
`nn.Linear` submodule) replaces the InternVL pipeline's hand-named LoRA
target modules.

`enable_thinking` matters only for models that support a reasoning mode
(Qwen3-family "Thinking" variants, etc.) -- it is a generation-time switch
(base-arm zero-shot eval, GRPO rollouts, val/test inference), passed to
`processor.apply_chat_template(..., enable_thinking=...)` and silently
dropped for models whose template doesn't accept it. It never changes the
SFT training target itself: **the assistant turn we supervise is always
just the JSON box array**, with no synthetic chain-of-thought text, since
we have no gold reasoning traces to teach specific `<think>` content
against. With `enable_thinking: true` on `qwen3vl_8b_thinking.json`'s
default, that means SFT teaches "respond with the box array" and leaves
whether-to-reason-first entirely to GRPO: rollouts are model-generated (not
teacher-forced), so the policy is free to open a `<think>` block if it
wants during sampling, and the reward -- which parses whatever JSON array
appears anywhere in the completion -- judges only the outcome. Whether
explicit reasoning before localization actually helps IoU is then a live,
reward-shaped question rather than something hand-authored. Flip the flag
to `false` for the simpler direct-answer behavior.

## 2. Data pipeline

```bash
cd scripts
python3 build_dragon6_raw.py          # walk Train/Val/Test, uniform filters -> per-domain raw JSONL
python3 build_dragon6_pools.py        # domain-balanced disjoint SFT + GRPO pools from Train
                                       #   --total-sft / --total-grpo to change the default 2000/5000
python3 build_dragon6_val.py          # domain-interleaved Val -> safe to slice with --val-size

python3 convert_to_chat_jsonl.py --in ../dragon_datasets/raw_sft_records.jsonl \
  --out ../dragon_datasets/sft_grounding.jsonl
python3 convert_to_chat_jsonl.py --in ../dragon_datasets/raw_grpo_records.jsonl \
  --out ../dragon_datasets/grpo_grounding.jsonl
python3 convert_to_chat_jsonl.py --in ../dragon_datasets/raw_val_interleaved.jsonl \
  --out ../dragon_datasets/val_grounding.jsonl

cd ../dragon_grpo
python3 build_test_split.py           # Test -> per-domain converted JSONL + contamination audit
```

## 3. SFT

```bash
cd scripts
python3 train_sft.py \
  --model-config ../configs/models/qwen3vl_8b_thinking.json \
  --train-jsonl ../dragon_datasets/sft_grounding.jsonl \
  --image-root ../Diagram_Attribution_Dataset \
  --output-dir ../outputs/sft \
  --epochs 3 --lr 1e-4 --per-device-batch-size 1 --grad-accum 16
```

Multi-GPU: this is a plain `transformers.Trainer` script -- launch with
`accelerate launch train_sft.py ...` or `torchrun --nproc_per_node=N
train_sft.py ...`, no bespoke launcher needed. Checkpoint written to
`outputs/sft/final/` is adapter-only (peft's own save format, tens of MB,
not a merged multi-GB model) -- see `scripts/lora_checkpoint_io.py`.

## 4. GRPO

```bash
cd dragon_grpo
python3 grpo_train.py \
  --model-config ../configs/models/qwen3vl_8b_thinking.json \
  --sft-checkpoint ../outputs/sft/final \
  --jsonl ../dragon_datasets/grpo_grounding.jsonl \
  --image-root ../Diagram_Attribution_Dataset \
  --val-jsonl ../dragon_datasets/val_grounding.jsonl --val-size 120 \
  --output-dir ../outputs/grpo \
  --group-size 8 --prompts-per-step 2 --save-every 50
```

Start with `--max-prompts 50 --group-size 2` as a pilot -- see §6 below
before committing a long run. Reward design (`scripts/box_matching.py`)
mirrors `dragon_sft_grpo`'s: dense in IoU (a box 30% too big scores ~0.6,
not 0/1), `w_miss > w_fp` (under-prediction penalized harder than an extra
box), token-level PPO-clip with a k3 KL penalty against the SFT policy
(GRPO adapter disabled via `peft`'s `disable_adapter()` -- no second model
copy in memory).

## 5. Evaluation

```bash
cd dragon_grpo
./run_eval_arms.sh ../configs/models/qwen3vl_8b_thinking.json base preds_for_eval/base
./run_eval_arms.sh ../configs/models/qwen3vl_8b_thinking.json sft  preds_for_eval/sft  ../outputs/sft/final
./run_eval_arms.sh ../configs/models/qwen3vl_8b_thinking.json grpo preds_for_eval/grpo ../outputs/sft/final ../outputs/grpo/grpo-step500

python3 three_arm_table.py --base preds_for_eval/base --sft preds_for_eval/sft --grpo preds_for_eval/grpo
```

`eval_script.py` is copied byte-for-byte from `dragon_sft_grpo` (the
official, model-agnostic metric script: MaxIoU / MeanIoU / GroupIoU /
Soft R,P,F1 / R,P,F1@τ) -- unmodified, so numbers are directly comparable
between the two repos as long as both feed it the same `[0,1000]`
xyxy-normalized box schema, which both do.

**Reading the base arm**: a low zero-shot score reflects format mismatch
(the model hasn't been trained on this exact JSON convention) as much as
grounding ability -- see `scripts/grounding_prompts.py`'s docstring. Treat
base→SFT as "did SFT teach the format", and SFT→GRPO as the localization
quality claim.

## 6. Before you trust a long run

This repo was authored without GPU or model access -- every script follows
established `transformers`/`peft` patterns (the same ones HF's own
multimodal SFT examples and `dragon_sft_grpo`'s proven design use), but
nothing here has been executed end-to-end. Before committing a multi-hour
run, check:

1. **`train_sft.py`, first few steps**: loss is finite and decreasing, not
   NaN. If label masking silently degenerated (e.g. the whole sequence
   supervised, or nothing at all), loss will look pathological immediately.
   Watch for the `[warn] sample ...: prompt/full common-prefix length ...`
   line in `GroundingSFTDataset.__getitem__` -- it fires when the
   chat-template prompt/full-conversation prefix match is shorter than
   expected, which is the label-masking boundary's early-warning signal.
2. **Adapter checkpoint size**: `outputs/sft/final/` should be tens to a
   few hundred MB (LoRA + connector, if `target_modules="all-linear""`
   caught it), not multiple GB -- a huge checkpoint means the LoRA wrap
   didn't take and the full base model params are being saved.
3. **GRPO rollout expansion**: with `--group-size 8`, print
   `gen.shape[0]` after the first `model.generate(...,
   num_return_sequences=8)` call -- it must be `8`, and the 8 decoded texts
   for one prompt must actually differ from each other (confirms
   `pixel_values`/image-grid metadata expanded correctly alongside
   `input_ids`, not just repeated the same single-image forward pass by
   accident).
4. **Decode sanity**: print one raw rollout's decoded text before parsing.
   If a `<think>` block is present in the model's actual output but
   `grounding_prompts.parse_pred_boxes` returns `None`, check whether
   `skip_special_tokens=False` actually made it into your version of the
   decode call -- `dragon_sft_grpo/README.md` documents losing a full
   training cycle to exactly this mistake on a different model.
5. **`enable_thinking` behavior**: with the shipped config
   (`enable_thinking: true`), generate one sample at low temperature before
   a full GRPO run and eyeball whether the model opens a `<think>` block or
   not -- either is fine (see §1), but knowing which mode you're actually
   training against changes how to read the reward curve.
